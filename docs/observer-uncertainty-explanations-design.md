# Observer Uncertainty Explanations — Design Spec

Status: Approved. Phase 1.5 — a reporting/XAI layer on top of the existing DSE
measurement feature (`docs/observer-uncertainty-design.md`). Does not change
what DSE measures, computes, or how it is used. Measurement-only guarantees
from Phase 1 (never gates Decider/Executor/Reflector/workflow, never a
pass/fail verdict) apply unchanged here.

## 1. Purpose

Raw DSE artifacts (`manifest.json`, `widgets.json`) give per-widget entropy
numbers and cluster contents, but reading them requires manually diffing JSON.
This feature adds a plain-English explanation of *what disagreed and how*,
generated by an LLM reading the existing cluster data — printed live to the
CLI during a run and collected into the final `run_overview.md` report.

This is explicitly a **reporting/explainability layer**, not a new
measurement. It reads DSE's existing output; it does not add new sampling,
new entailment judging, or any new decision logic.

## 2. Scope boundary (carried over from Phase 1)

The explanation text must never:
- Use decision/quality words: uncertain, unreliable, failed, wrong, correct,
  confident, accurate, reliable, good, bad, pass, fail, accepted, rejected,
  certain.
- Characterize the *model's* competence ("the model struggled/failed to...").
- Imply a threshold was crossed or a judgment was made.

The explanation **may**:
- State counts and proportions ("3 of 5 interpretations said X, 2 said Y").
- Distinguish *wording variance* (same underlying widget, different phrasing)
  from *conflicting readings* (different interpretations of role/function) —
  this is a factual description of the cluster data's shape, not a judgment
  about whether disagreement is good or bad.

Worked example (hand-crafted, since two real test runs against 33 widgets
across two different screens produced only wording/grouping variance, never a
genuine role contradiction — see Section 8):

> Widget 9 (no visible text): 3 of 5 interpretations described it as a
> share/export icon button, while 2 interpretations described it as a
> decorative text divider with no interactive function. These are conflicting
> readings of the same element's role, not just wording differences.

Real example (from actual DSE data, widget 7, 3 clusters):

> Widget 7 (top-right icon button, 5 samples, 3 distinct interpretations): 2
> samples described it as "Action Menu Icon Button — settings/overflow icon",
> 2 samples described it as "Icon Button — Action menu item
> (settings/more options)", and 1 sample described it as "Action Menu Icon —
> settings/overflow icon". All three interpretations describe the same icon
> as an action/settings/overflow menu button, differing mainly in exact
> wording and whether "menu" or "settings" was emphasized.

## 3. Architecture

### 3.1 New module: `core/uncertainty/explainer.py`

```
def explain_step_uncertainty(llm, widgets_data, step_context) -> str | None
```

- `widgets_data`: the `per_widget` list already computed by
  `ObserverUncertaintyService.measure_from_samples` (has `element_id`,
  `raw_dse`, `clusters`, plus widget metadata needed for context — see 3.3).
- `step_context`: dict with `screen_desc` (same value passed to the
  entailment clusterer).
- Filters to widgets where `raw_dse > 0`. If the filtered list is empty,
  returns `None` immediately — **no LLM call is made**.
- Otherwise builds one prompt covering all uncertain widgets in the step,
  sends it via the passed-in `llm` client, applies the banned-word check
  (3.4), and returns the final text or `None` on unrecoverable failure.

This function is pure with respect to the LLM call — it does not write
files or print anything. Callers handle I/O.

### 3.2 New prompt module: `shared/prompts/uncertainty_explainer_prompts.py`

Separate file, matching the existing pattern where `entailment_prompts.py` is
kept separate from `observer_prompts.py`. Contains:

- `EXPLAINER_SYSTEM_PROMPT`: instructs the LLM to describe disagreement
  factually (counts, what each cluster said), explicitly bans the word list
  from Section 2, and gives both worked examples from Section 2 as few-shot
  reference.
- `EXPLAINER_HUMAN_TEMPLATE`: takes `screen_desc` and a formatted list of
  uncertain widgets, each with `element_id`, `text`, `role`, and its cluster
  contents (the actual differing description strings, not just counts).

### 3.3 Context fields per uncertain widget

Per widget, the prompt includes:
- `element_id`
- `text` (widget's visible text, may be empty)
- `role` (e.g. `icon_button`, `button`, `text` — from XML metadata, same
  field already used by `WidgetContext` in `clusterer.py`)
- Full cluster list: each cluster's member description strings (not just the
  cluster count) — this is what lets the explainer say "described it as X"
  rather than "widget 7 had 3 clusters."

This requires `ObserverUncertaintyService` to pass widget `text`/`role`
through to the explainer call — currently `per_widget` entries do not carry
these fields (only `element_id`, `responses`, `clusters`, etc.). The service
must look them up from the original `widgets` list it already receives.

### 3.4 Banned-word enforcement

After generation:
1. Lowercase-scan the returned text against the fixed banned-word list
   (Section 2). Word-boundary match (e.g. "pass" must not match "passed" — 
   use regex `\bword\b`).
2. If a match is found: retry **once**, appending a stricter reminder to the
   human message ("Your previous response used judgment language. Describe
   only what was said and how often — do not characterize reliability or
   correctness.").
3. If the retry also matches: discard the explanation entirely. Treat
   identically to an LLM call failure (Section 3.6) — log and return `None`.
   Do not partially strip sentences (rejected in brainstorming as producing
   choppy output).

### 3.5 Integration point: `ObserverUncertaintyService.measure_from_samples`

After building `per_widget` and `manifest` (existing code, unchanged), add:

```python
explanation = explain_step_uncertainty(self.llm, per_widget_with_context, {"screen_desc": screen_desc})
manifest["explanation"] = explanation  # None if nothing uncertain or generation failed
```

Note: `explanation` is also stored in the manifest for completeness/audit
trail, in addition to the separate `explanation.txt` file (3.7) — the file is
the primary artifact for human reading; the manifest field lets automated
tooling check whether an explanation was generated without a second file
read.

### 3.6 Failure handling

If the explainer LLM call raises an exception (network error, malformed
response, etc.): catch, log via the existing process logger at DEBUG/WARN
level, set `explanation = None`. The step continues completely normally — DSE
numbers, clusters, and all other artifacts are unaffected. This matches how
DSE sampling failures are already handled (never destabilize the run).

### 3.7 Artifact: `explanation.txt`

New file written by `write_uncertainty_artifacts` (extend
`core/uncertainty/artifacts.py`) at `{step_dir}/uncertainty/explanation.txt`,
**only when `explanation is not None`**. Plain UTF-8 text, no JSON wrapping.
Not written when there was nothing uncertain, and not written when
generation failed after the retry — both cases leave the file simply absent
(not an empty file, not a placeholder), consistent with the "skip silently"
decision from brainstorming.

### 3.8 CLI output

In `ObserverAgent._maybe_run_uncertainty` (`agents/observer_agent.py`), after
`service.measure(...)` returns:

- If `manifest["explanation"]` is `None` **and** all widgets had
  `raw_dse == 0`: print
  `[Uncertainty] No disagreement detected across {N} widgets.`
  (N = widget count measured, i.e. `manifest["widgets_measured"]`). This is a
  free, code-only line — no LLM call, just a count already in the manifest.
- If `manifest["explanation"]` is `None` **but** some widgets had
  `raw_dse > 0` (i.e. the explainer call itself failed): print nothing extra
  (matches "skip silently" — the DSE numbers are still visible via the
  existing per-widget print loop already in `_maybe_run_uncertainty`).
- If `manifest["explanation"]` is a string: print
  `[Uncertainty] {explanation}`.

### 3.9 Final report: `run_overview.md`

In `write_run_overview` (`core/utils/output_writer.py`), add a new
`## Observer Uncertainty` section, positioned after `## Step Summary` and
before `## Final Verdict`. Populated by reading `explanation.txt` from every
step folder under the run that has one (glob `steps/*/uncertainty/
explanation.txt`, sorted by step number). Each entry rendered as:

```
### Step {N}

{explanation text}
```

If zero step folders have an `explanation.txt`, the entire
`## Observer Uncertainty` section is omitted from the report (not printed as
an empty section or "N/A") — matches the same "absence over placeholder"
principle used elsewhere in this design.

This requires `write_run_overview` to receive (or discover) the run's
`output_dir` to glob step folders — it already receives `output_dir` as a
parameter, so this is a glob against an already-available path, no new
parameter needed.

## 4. Data flow

```
ObserverAgent._maybe_run_uncertainty
  -> ObserverUncertaintyService.measure_from_samples (existing DSE math, unchanged)
     -> explain_step_uncertainty(llm, per_widget+context, step_context)
        -> [0 uncertain widgets] return None, no LLM call
        -> [N uncertain widgets] build prompt -> llm.invoke -> banned-word scan
           -> [clean] return text
           -> [violation] retry once -> [clean] return text
                                     -> [violation again] return None
     -> manifest["explanation"] = result
  -> write_uncertainty_artifacts (extended: writes explanation.txt if present)
  -> CLI print (per 3.8)
  -> (at run end, separately) write_run_overview collects explanation.txt files
```

## 5. Cost profile

At most 1 additional LLM call per step (0 when nothing is uncertain), plus up
to 1 retry on a banned-word violation (worst case 2 calls). Reads only
already-generated cluster data — no new sampling calls, no new entailment
judge calls. Negligible relative to DSE's existing 150–300+ calls per step
for a widget-heavy screen.

## 6. Testing requirements

- `explain_step_uncertainty` returns `None` with zero LLM calls when all
  widgets have `raw_dse == 0` (mock LLM, assert `invoke` not called).
- Returns generated text when passed uncertain widgets (mock LLM).
- Banned-word scan: unit test the regex against the full word list, including
  word-boundary false-positive checks (e.g. "passed the widget" must not
  false-positive on "pass").
- Retry-then-discard path: mock LLM to return a violating response twice,
  assert `invoke` called exactly twice and final result is `None`.
- `write_uncertainty_artifacts` writes `explanation.txt` only when
  `explanation` is not `None` — test both branches.
- `write_run_overview`: test with 0, 1, and 2+ step folders containing
  `explanation.txt`; assert section omitted vs. present with correct content
  in each case.
- Integration test (extends existing
  `test_observer_uncertainty_integration.py` pattern): full
  `measure_from_samples` call with a mock LLM/clusterer producing multiple
  uncertain widgets, assert `manifest["explanation"]` is populated and
  contains no banned words.

## 7. Non-goals

- Not a summarization of the entire step (Decider/Executor/Reflector
  actions) — scoped strictly to Observer DSE disagreement.
- Not a per-widget individual explanation call — one call per step, covering
  all uncertain widgets together (cost decision from brainstorming).
- Does not change `threshold`, `calibration_status`, or any other Phase 1
  guard field — those remain exactly as specified in the original DSE design.
- Does not attempt to explain *why* the underlying LLM produced different
  descriptions (that would require introspecting the base LLM, out of
  scope) — only describes *what* the differences were.

## 8. Open items / explicitly deferred

- No genuine "role contradiction" case (e.g. button vs. text label) was
  found in two real test runs (33 widgets across two different screens from
  the same app) — all observed disagreement was wording/grouping variance on
  the same underlying widget identity. The Section 2 "conflicting readings"
  example is therefore hand-crafted, not drawn from real data. If real
  contradictions surface in future runs, the explainer prompt's handling of
  that case should be re-validated against real output.
- Whether explanation quality/tone holds up across different apps/screens
  (this design was validated only against the Notes app scenario data
  available at spec time) is not verified — flag as a follow-up once more
  scenario data exists.

## 9. Acceptance criteria

- [ ] Prompt module created per 3.2, separate from `observer_prompts.py`.
- [ ] Banned-word enforcement implemented per 3.4 (scan + 1 retry + discard).
- [ ] `ObserverUncertaintyService` integration per 3.5, widget text/role
      threaded through to the explainer.
- [ ] `explanation.txt` artifact written per 3.7 (present/absent cases both
      tested).
- [ ] CLI output implemented per 3.8 (all three branches).
- [ ] `run_overview.md` section implemented per 3.9 (0/1/N step cases).
- [ ] All tests in Section 6 pass.
- [ ] No existing DSE test regresses (guardrail fields unchanged, existing
      manifest/widgets.json shape unchanged except for the additive
      `explanation` key).
